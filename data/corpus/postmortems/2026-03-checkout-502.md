# Postmortem: checkout-api 502 errors after release v2.31.0

Date: 12 March 2026. Severity: SEV2. Duration: 38 minutes. Author: Commerce Platform.

## Summary

Release v2.31.0 of checkout-api changed the application server from a library default to an explicit
configuration. About 9% of `POST /checkout` requests returned 502 for 38 minutes. Roughly 4,100
customers saw an error at the payment step and about 1,300 abandoned their basket.

## Timeline (UTC)

- 14:02 v2.31.0 finished rolling out.
- 14:09 The 502 rate alert fired at 3%.
- 14:14 On-call opened the incident and found the release in the Deploys dashboard.
- 14:21 Rollback to v2.30.4 started after a discussion about whether payments-gateway was at fault.
- 14:40 502 rate back to baseline.

## Root cause

The release replaced the application server's default keepalive timeout of 120 seconds with an
explicit value of 60 seconds. The nginx sidecar keeps upstream connections for 75 seconds. For 15
seconds out of every 75 the application had already closed a connection that nginx still considered
open, and a request sent on it failed with a 502.

## What went well

- The alert fired within seven minutes.
- The rollback itself took three minutes and worked first time.

## What went badly

- We lost 12 minutes looking at payments-gateway, which was healthy. Nobody checked the Deploys
  dashboard until the second responder joined.
- The configuration change was not mentioned in the release notes, so reviewers did not see it.

## Action items

1. Add a startup check that fails when the application keepalive is not longer than the sidecar's
   (owner: Commerce Platform, due 26 March, done).
2. Put configuration changes in a dedicated section of the release notes template.
3. Add "check recent deploys" as the first step in the general triage runbook.
