# Enterprise integrations and text-to-SQL: findings (AIENG-54 to AIENG-58)

Run on 17 Oct 2026. Evidence: [text-to-SQL with the real model](2026-10-17-text-to-sql.md)
(`gpt-6-luna`, the ops schema on a scratch database dropped afterwards) and the test suite (fake
Jira and fake CMDB in process, the reader role against real PostgreSQL). Design, contracts,
evaluation sets and hypotheses H35 to H39 were committed before any W09 code:
[roadmap-w09.md](../../../docs/roadmap-w09.md), [contracts](../../../docs/notes/integration-contracts.md).

## The layers are not as redundant as the design said

The design called for four layers, "any one of which stops a bad query". To test that claim, I ran
all 20 attacks **straight against the reader role, with the validator bypassed**:

| Stopped by the database as well | Stopped only by the validator |
|---|---|
| writes, DDL, `INTO`, `FOR UPDATE`, a DELETE in a CTE (read-only transaction); `COPY` to a file, `SET ROLE`, `pg_authid`, `pg_read_file`, `public.incidents` (privileges); `pg_sleep` (timeout); two statements, unknown columns, `dblink` (errors) | `information_schema.tables` (100 rows), a join to `pg_user` (every role in the cluster), `set_config(...)` |

PostgreSQL grants read access to most of its catalog to every role, and no grant can take it away
from one role alone. So for catalog reads, the validator is the only wall. Nothing there is
incident data, but table and role names are reconnaissance. `set_config` ran too, but it cannot
switch off the timeout that matters, because every query sets its own `SET LOCAL
statement_timeout` inside its transaction. The real fix is to put the ops data in a database (or
cluster) of its own, whose catalog has nothing worth reading. It is recorded as a risk.

## What the spot checks found in the validator

Two problems that no test covered, found by reading the validator's output before trusting the
45/45 first run:

1. **A false refusal.** `select NAME from OPS.SERVICES` was refused, although PostgreSQL folds
   unquoted names to lower case. The validator now normalises identifiers the same way (a quoted
   `"OPS"."SERVICES"` keeps its case and is still refused).
2. **An information leak.** `WHERE name = (SELECT current_user)` was accepted. Identity functions
   (`current_user`, `session_user`, `current_database` …) are now refused.

## The real-model run

- **14 of 15 correct.** The miss, s08 ("how many alerts did each service fire in October?"),
  `LEFT JOIN`ed from `services`. So it also listed the one service with no October alerts,
  with a count of 0. That is arguably the better answer, but the pre-registered rule compares row
  counts (9 against 8), so it is scored wrong.
- The model's SQL was more defensive than the references: explicit `CAST(... AS TIMESTAMPTZ)`,
  `RANK()` for "the most", a tie-break on `id`. Every query passed the validator.
- **All 8 malicious questions were declined by the model.** None reached the validator, so this run
  shows the prompt layer working, not the validator. The validator's evidence is the attack set.
  This is the reason the layers are tested one at a time, with the others removed.

## Cost

23 model calls, 17,030 input and 3,129 output tokens: about **$0.07** at the assumed price. The
adapters' tests use fakes and cost nothing. W05 to W09: about $1.09 of the $5 cap.

## Limits

The fakes implement the parts of Jira and of a SOAP CMDB that the adapters use; real services
paginate, version their APIs and fail in more ways. Fifteen questions over five tables is a small
benchmark; the matching rule is strict on row counts by design.
