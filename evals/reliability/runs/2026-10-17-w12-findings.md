# Production reliability and failure engineering: findings (AIENG-69 to AIENG-73)

Run on 17 Oct 2026, on one laptop (load generator, one uvicorn process, PostgreSQL in Docker).
Evidence: [the load baseline](2026-10-17-load.md), [how the first bottleneck finding was
wrong](2026-10-17-measurement.md), [request bursts](2026-10-17-burst.md), and the tests named below.
Design and hypotheses H50 to H53 were committed before any W12 code:
[roadmap-w12.md](../../../docs/roadmap-w12.md). No real model calls this week: the model was
simulated from the latencies and token counts of the real W07 run.

## The hypotheses

| | Prediction | Result | Verdict |
|---|---|---|---|
| **H50** | At 10 responders, triage P95 < 15 s, no errors, the bottleneck visible in traces | P95 8.3 s, 0 errors; the traces put 95% of a run in the two model steps | holds |
| **H51** | Every dependency failure ends in its named state; no silent wrong answer | model (all routes, primary only), retrieval (slow, broken), database (down, down mid-run), graph, CMDB, ticket system: each ends as designed (`test_dependency_failures.py` and earlier tests) | holds, after two fixes |
| **H52** | One incident, one decision, one ticket under concurrency; a killed server's run resumes | 50 → 1 incident, 20 → 1 decision, 10 → 1 ticket, and a SIGKILLed server's run resumed after restart with each model step once (`test_concurrency.py`) | holds, after one fix |
| **H53** | `/status` reports the right tier under each failure | FULL, REDUCED (graph, CMDB), MANUAL (database, model breakers) (`test_status.py`) | holds |

## The load baseline

At most 25 responders per client process; each responder creates, triages, reads and approves:

| Responders | Triage P50 / P95 / P99 | Create P95 | Decide P95 | Throughput | Errors |
|---|---|---|---|---|---|
| 1 | 6.4 / 6.4 / 6.4 s | 13 ms | 52 ms | 0.12 triages/s | 0 |
| 10 | 6.4 / 8.3 / 8.3 s | 23 ms | 71 ms | 1.0/s | 0 |
| 20 | 5.9 / 8.6 / 9.5 s | 62 ms | 95 ms | 1.8/s | 0 |
| 50 | 6.3 / 9.5 / 9.6 s | 120 ms | 169 ms | 4.3/s | 0 |
| 100 | 7.7 / 9.1 / 9.3 s | 196 ms | 196 ms | 8.9/s | 0 |

- **The bottleneck is the model**: the two model steps are about 95% of a run at every level.
  Throughput scales linearly to 100 because runs mostly wait.
- **The API's own overhead per run** (checkpoint writes, the event loop) grows from 42 ms at 1
  responder to 402 ms at 100. Larger connection pools take 10 to 15% off it at 100.
- **Estimated cost per triage: $0.019** (two calls at the recorded 2,010 / 449 tokens, assumed
  price).

## The finding I had to retract

The first runs drove all responders from one client process. Creating an incident slowed from 9 ms
to 400 ms at 100 responders, and I blamed the connection pools; the commit said so. Doubling the
pools changed nothing; a burst of `/health` (no database) was slow too; and the same 100 requests
took 430 ms from one client process and 47 ms from four. The load generator was the bottleneck.
The runner now splits clients, and the earlier report is marked superseded. Lesson: measure the
measuring tool.

## What the tests found and fixed

1. **Retrieval could hang a run.** A vector store that does not answer had no bound. Retrieval now
   times out at 5 s (`RetrievalTimeout`): no evidence, review, nothing invented.
2. **A run interrupted by a dead process stayed `running` forever.** The process cannot record its
   own death. At startup, runs older than `INCIDENTOPS_STALE_RUN_AFTER_S` (900 s) are marked
   `failed` (`StaleRun`) and can resume; a slow run is left alone.
3. **Concurrent ticket writes duplicated.** Ten concurrent writes for one run made ten Jira issues:
   the sink's search-then-create is not atomic. A PostgreSQL advisory lock on the run around the
   write now serialises them across processes.

## Decision

[ADR-009](../../../docs/adr/009-reliability-and-degradation.md).

## Limits

The model was simulated: real providers add their own rate limits and slow tails. One machine ran
everything, so numbers are relative. One API process was measured; more processes were not.
